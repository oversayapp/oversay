## Confirmed and fixed: the save helper followed a planted link (medium)

`files.rs` `write_atomically` writes a temporary file with a fixed name (`.<name>.tmp`) beside the file it saves, with `fs::write`, which follows a symbolic link. A deck or workspace folder from someone else that carries a hidden link with that name makes the start-up tidy and the folder watcher (`quick.rs` `tidy_decks`) write the deck text into the link's target, and turn the deck into a link to it. It was reproduced twice with an exact copy of the function inside a network-blocked, write-confined sandbox, once by the hunter and once independently, before the fix.

Low likelihood (a crafted folder must be put in the Decks folder and the link must survive the transport), high impact (a file the person owns is overwritten with text the sender wrote). Every other save path used the same helper.

**Fixed on 2026-11-17 in [PR 42](https://github.com/oversayapp/oversay/pull/42)** (merge commit `8dd4cce`): the helper now writes to a new temporary file with a unique name that must not already exist, syncs it, and renames it over the target, removing it on failure. One change covers every caller. A regression test plants a link at the old temporary name and checks it is left alone; it failed before the change and passes after. The fix was in `main` before any `v0.4.0` tag, so no tagged release carries the bug. Builds handed out earlier to testers (0.1.0 and the rolling builds of `main`) do, and testers move to 0.4.0 by installing it by hand.

## Needs validation: who can reach the release secrets

A pushed `v*` tag or a manual run with "sign" ticked builds and publishes a signed release from any commit. The `release` environment has no deployment rule or reviewer, and the update key is a repository secret that the Windows and macOS jobs read on any manual or tag run. Pull requests, forks and Dependabot reach no secret. Whether this matters depends on who besides the owner can push a tag or run workflows, which is a GitHub setting the audit did not read. Owner check: collaborators, apps and deploy keys; a tag rule for `v*`; the environment's deployment rules and reviewers; the scope of each secret.

## Hardening notes (not findings)

- Sign the update packages in a step after the build, so the update key is not in the environment of the step that runs dependency build scripts.
- The runnable-type list in `resources.rs` is a denylist; an allowlist would be sturdier.
- `checked()` in `quick.rs` accepts a deck file that is itself a symlink; reading follows it.
- `style-src 'unsafe-inline'` with `dangerousDisableAssetCspModification` for styles.
- One open Dependabot alert, `glib`, which is Linux only.

## What was covered, and what was not

**Covered:** the pull-request trigger and token scope; expression injection in the workflow; the updater's check and install path; the local test feed; the speech-model download.

**Deferred (not reviewed in this pass):** macOS and Windows native code and its unsafe blocks; all dependencies beyond `cargo audit` and `npm audit`; the **skill installer**, which writes into the user's agent folders at every start (ranked highest-risk by the coverage critic); the resource opener's denylist; IPC path inputs that are links; Markdown rendering in the overlay windows; what a deep link does after the person consents; WAV parsing in recorded sessions; the `--check` command; workspace folders beyond the save helper; the frontend file parsers; clipboard read; the CI cache; overlay-window capabilities. A standard or deep run would cover these.

## How the run was checked

The first verifier of the release lead rejected it on a premise the parent stated without having established it (that the owner is the only person with write access). That was not known, so a fresh verifier re-checked it with the unknown stated as unknown, and it stays a lead.
